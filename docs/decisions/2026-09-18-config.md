# One config, one `get()` — decided before v1, built after it

**Raised 18 September 2026 by the design review. Drafted 20 September. Proposed, not decided, and
nothing here ships before the beta stabilises.** No key is deleted and nothing is refactored by this
record.

Every number below was counted on 20 September, not carried over from the review.

---

## §1 · Where the configuration actually is

| | |
|---|---|
| keys declared in `.env.example` | **81** (the review said 78) |
| `settings.RUNTIME` — read through `get()` at the moment of use | **54** |
| `settings.BOOTSTRAP` — read once by Docker or at process start | **16** |
| `settings.RETIRED` — rows kept, nothing reads them | 4 |
| keys read somewhere in `app/` via `os.getenv` | **35** |
| keys read somewhere in `app/` via `settings.get` | **37** |

`RUNTIME` by group: sources 15, alerts 12, node 10, agent 7, integrations 4, keys 3, packs 2, issues 1.
Also declared: 32 keys in `PUBLIC`, 6 in `CHOICES`, 14 in `OUTWARD`.

### Four idioms that look identical at the call site

1. `settings.get("KEY", default)` — the design.
2. **Eleven accessor functions in `app/main.py`** — `def TG():`, `def PARENT():`, `def ACT_TOKEN():` …
   each a one-line wrapper around (1). Harmless, and it means the call site says `PARENT()` and a
   reader cannot tell from the name whether the database is consulted.
3. **`cfg()` in `app/agent_loop.py`** — `CFG.get(k) or os.getenv(k) or d`, a *fourth* precedence order,
   against a dict refreshed once a minute from `/settings/raw`.
4. `os.getenv("KEY")` — the environment, and the database value is ignored.

### Four RUNTIME keys are read through `os.getenv` anyway. Two are bugs.

| key | where | verdict |
|---|---|---|
| `ALERT_LOCALE` | `app/agent_loop.py:50`, at import | **bug.** A household sets its language on the dashboard; the page and the alerts change and **the Telegram bot stays in English**. Module-level, so even the minute-ly refresh does not reach it. |
| `NODE_KIND` | `app/main.py:842` | **bug.** It is in `RUNTIME` and in `PUBLIC`, so Set up offers it — and changing it there changes nothing at that endpoint. |
| `ACT_TOKEN` | `app/reticulum_bridge.py:179` | **structural.** That container has no database. Rotate `ACT_TOKEN` from the dashboard and the app accepts the new one while the bridge keeps presenting the old: **the LXMF act path stops working silently.** |
| `RETICULUM_ALERT_DESTINATIONS` | `app/reticulum_bridge.py:41` | **structural**, same reason. |

**The two structural ones are the whole argument of this record.** They are not carelessness. The
`settings` table lives in Postgres and only the `app` container has credentials for it, so *no amount of
discipline* makes a runtime setting reach the bridge, the agent container or `backup.sh`. A file can.

### Three more facts that a target has to answer

- **`RETICULUM_PRESENCE`, `RETICULUM_PRESENCE_RES` and `UI_LAYOUT` are in `RUNTIME` and not in
  `.env.example`.** They exist only if something writes a row. `update.sh`'s merge loop reads
  `.env.example`, so these three can never be added to an existing node's `.env` by an update.
- **`backup.sh:44` runs `pg_dump --exclude-table-data=settings`.** Every dashboard choice a household
  has made is absent from every backup, by design — the table carries the Telegram token and dumps
  travel to a NAS. So `planetai restore` silently reverts a household to its `.env`, and the only
  notice of that is a sentence in `planetai restore`'s output.
- **Six `.env` keys have no reader in `app/`** — `AGENT_MODEL`, `POSTGRES_PASSWORD` (both
  `docker-compose.yml`), `EE_SERVICE_ACCOUNT`, and `THINGDATA_INSTANCES`/`_MAX`/`_SCALE` (the packs).
  Not dead; read somewhere `app/` is not. A target that assumes `app/` is the only reader breaks them.

## §2 · The target

**`planetai.yml`, in the node folder, is the node's configuration. `.env` becomes bootstrap only.**

```
planetai/
  .env            what Docker and the process need BEFORE the app exists
  planetai.yml    everything the node decides at the moment of use
```

Mounted **read-only into every container**, the way `./config` already is — which is precisely what the
`settings` table cannot do, and why this is a file and not a better table.

**What stays in `.env`**, and it is bigger than the review's "under 15" because the honest list is:

`POSTGRES_PASSWORD` · `ADMIN_TOKEN` · `APP_PORT` · `DATA_DIR` · `COMPOSE_PROFILES` · `MQTT_HOST` ·
`OLLAMA_URL` · `AGENT_MODEL` · `NODE_NAME` · `NODE_CITY` · `NODE_LAT` · `NODE_LON` · `NODE_TZ` ·
`NODE_SCALE` — **14**, plus `BACKUP_DIR`, `BACKUP_REMOTE`, `BACKUP_KEEP`, `EXPORT_ENABLED`,
`IPFS_PUBLISH`, `POLL_SECONDS`, which `backup.sh` reads from `.env` with its own reader and which
therefore move only when `backup.sh` learns to read the file. **20 today, 14 after `backup.sh` moves.**

**One `get()`.** `settings.get(key, default)` reads the file, cached, and is the only reader. The eleven
accessor functions in `main.py` stay — they are a readability convenience, not a second mechanism — but
`cfg()` in `agent_loop.py` and every `os.getenv` of a `RUNTIME` key go.

**The `settings` table becomes a cache of the file, then is dropped.** The GUI writes the file (through
the app, which is the only process that should) and the table holds nothing the file does not. Once
nothing reads it, it is dropped in a release that says so. **And the backup problem disappears with it**
— a file is a file, and `backup.sh` can copy it, which it cannot do with a table it is excluding on
purpose.

## §3 · The migration, and its blast radius per step

| step | what | blast radius | rollback |
|---|---|---|---|
| **0** | Fix `ALERT_LOCALE` and `NODE_KIND` to read through `get()`. Two lines. | A household's language reaches the bot; Set up's Kind starts working. | revert |
| **1** | `planetai config migrate` writes `planetai.yml` from `.env` + the `settings` table, **leaves both untouched**, prints a diff. | none — it only writes a new file | delete the file |
| **2** | `settings.get()` reads file → table → env, in that order. Two releases. | a node with no file behaves exactly as today | remove the file read |
| **3** | The bridge and the agent read the file. `ACT_TOKEN` and `ALERT_LOCALE` stop being env-only. | **the two structural bugs close**; a mis-mounted file makes those containers fall back to env, i.e. today's behaviour | unmount |
| **4** | GUI and `planetai config` write the file, not the table. | a household's choice is now in a backup for the first time | write both for one release |
| **5** | `backup.sh` reads the file; the six remaining keys move out of `.env`. | `backup.sh` is the one script with its own `.env` reader | keep the reader |
| **6** | Drop the `settings` table. | irreversible — do it a release after nothing reads it, and only then | the dual-write of step 4 is the safety net, and it must have run |

**What it costs the two live nodes:** one command and one restart, at step 1, and nothing at all until
step 4 — up to which point `planetai.yml` exists and is ignored. Node #1 and Menorca keep every value
they hold, because step 1 reads the values they hold rather than the defaults.

**Do not start at step 6.** The order above is the whole design: every step before 4 is reversible by
deleting a file.

## §4 · What is not decided here

- **Whether `planetai.yml` is YAML.** It is the obvious choice — `config/rules.yml`, `channels.yml` and
  every `pack.yaml` already are, and the app has `pyyaml`. The counter-argument is that the host CLI
  must parse it too and is pinned to Apple's Python 3.9 stdlib, which has **no YAML**
  (`tools/check_cli_python.py` refuses `import yaml` in a CLI snippet, by name). So either the CLI asks
  the app for its config over the API — which it already does, `setting()` in `bin/planetai` — or the
  file is JSON. **Recommend YAML plus the API**, and note that this couples the two records: a node
  whose app is down would then have no CLI path to its own config, which is exactly when somebody needs
  one.
- **Whether `UI_LAYOUT` belongs in it.** It is a blob of JSON written by the dashboard's Arrange mode,
  not a setting a person types. It may want its own file.
- **The date.** Nothing here ships before the beta stabilises. Step 0 is two lines and two bugs and can
  go any time; everything after it waits.

---

## §5 · Why this is worth writing down now and not doing now

The cost of the current shape is paid by a household that changes its language and finds the bot did
not change, and by a keeper who rotates a token and finds the radio stopped — neither of whom will
report it as a configuration bug, because neither of them can see the seam. That is the argument for
fixing it.

The argument for not fixing it this month is that `.env` + a table works, two nodes are live on it, and
the beta's job is to find out whether households act on alerts. A seven-step migration through the
configuration layer during that is how a beta stops producing evidence.

**So: step 0 now, the rest after v1, and this record is what stops it being re-derived from scratch.**
