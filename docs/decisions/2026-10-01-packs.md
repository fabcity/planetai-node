# Packs: core, community, and the door between them

**Question.** A city's packs arrived on 30 September as a fork of the whole node (#152): three packs, the shared
issue files edited around them, and two dashboard rows written into the shell. Which packs belong in the release,
where do the others live, how does a node get them, and how does one move from the second group to the first?

## What Tomas has said

On 1 October 2026, in the session that reviewed #152:

- Packs that are not core sit outside the release.
- Community packs are listed separately, and a node adds the ones it wants. That was the idea from the beginning.
- A community pack can become a core pack and go into the release.
- A pack adds to the main issues when it has something to add.
- Packs need room on the dashboard, and a way to sit in it without bringing a design of their own.

The rest of this record is a recommendation for how to do that. Nothing below is decided until the line at the end
is filled in.

## Recommendation

**1. Two tiers.**

| | core | community |
|---|---|---|
| lives in | `packs/` in this repository | its own repository, never this one |
| reaches a node | in the release | `planetai packs add <git url>`, which clones it into `packs/<id>` |
| gates | `make lint && make test`, every commit | its own tests, and the community index's CI |
| maintained by | this repository's maintainers | its author |
| code (`adapter.py`) | runs with `PACKS_ALLOW_CODE=1` | the same, and nothing more |

The node needs no change to load a community pack: it loads any folder under `packs/` with a `pack.yaml`, and
`planetai update` leaves a folder it does not track alone. `docs/PACKS.md` says so since #153.

**2. A community index, listed separately.** One repository holds a list of community packs: where each lives,
what it reads, who wrote it, which node versions it was tested on. `planetai packs` prints core and community packs
under separate headings. Being listed is not being reviewed, and the list says so on every entry.

**3. Promotion is a pull request.** A community pack becomes core when a pull request moves its folder into
`packs/`, it passes every gate, and a maintainer here agrees to keep it. The tests a reviewer should ask for:

- it is useful beyond the place it was written for, or it is the reference for a pilot city;
- its data is openly licensed, and its README says under which licence;
- it has offline tests, registered in `tests/all`;
- somebody here will answer for it when it breaks.

The author line keeps the original author.

**4. A pack adds to an issue; it never replaces one.** Issues already take in a pack's rules and metrics by its
`domain:` (`packs: domains:` in each `app/issues/*.yml`). Extend the same claim to two things a pack cannot add
today:

- **Readouts.** A pack declares `readouts:` for an issue in its own manifest, and the node merges them in while the
  pack is installed. PSI and wind on Air, WBGT on Heat and the beach band on Coast would then travel with the
  Singapore packs instead of living in the shared files.
- **The region source.** An issue's `region:` names an ordered list of sources, and the first with a fresh reading
  wins. Air becomes "NEA, then CAMS": a node without the NEA pack reads CAMS as it does now. This is the order
  `AGENTS.md` already gives for "outside" (own sensors, then public references, then the model), applied to the one
  column that does not follow it.

**5. Community packs declare their dashboard sections; only core ships script.** A section in the page reads the
same browser storage the page keeps the admin token in, so a pack's own JavaScript would hold admin rights on every
node that installs it. Instead, a community pack describes its section as data: the stage, the title, which of the
four card kinds (readout, stack, series, row) and which metrics fill it. The shell draws it with its own components,
so it looks like the rest of the page, the visual gate measures it, and the node still computes what the page
draws. A section that needs script is a reason to promote the pack.

**6. `requires:` is enforced.** Every manifest says which node versions it needs (`requires: { node: ">=0.40.0" }`)
and nothing reads it. The loader should refuse a pack its node is too old for, with one line in the log and in
`planetai packs`. This matters once packs are no longer released with the node they were written for.

## What happens to the packs here now

Every pack in `packs/` today is core by this record, including the three whose author line says otherwise
(`xiaomi-air`, `posidonia`, `example-cooking-hours`). Whether any of them moves out is a decision per pack, and
not this one. Singapore's three (`singapore-nea`, `singapore-beach`, `fire-smoke`) start as community packs; Saad
has been asked to move them to a repository of his own (#152).

## Cost, in the order it should land

1. This record.
2. `planetai packs add <git url>`: clone into `packs/<id>`, refuse an id a core pack already has, then
   `planetai packs install`. Bash and Python 3.9's standard library only, like the rest of the CLI. One test.
3. The community index repository, with CI that runs this node's `tools/check_rules.py` and each pack's own tests
   against the node's `main`, on a schedule as well as on a push: a gate that reads another repository's `main`
   goes stale without a commit of its own.
4. Pack readouts and the ordered region list, in `app/issues/`. `tests/test_issues_engine.py` replays node #1 and
   must come out identical.
5. Declared sections in the shell. This is the design work. Singapore's two wall rows are the first case, and they
   may show that four card kinds are not enough.
6. `requires:` at load time. Small.

## What gets harder

- **Promotion collides with a clone.** A node that cloned a community pack into `packs/<id>` and then updates to a
  release where `<id>` is core: on a git checkout, `git pull --ff-only` refuses to overwrite the untracked folder;
  from the tarball, the release's files are unpacked over the clone's. `planetai update` should notice a clone where
  a core pack is arriving and say what to remove before it goes on.
- **Gates move out of this repository.** A community pack is tested where it lives and by the index, not here.
- **Trust.** A community code pack runs with this node's privileges, as a core one does. The index has to say
  which entries somebody has read.

## Open for Tomas

1. **The word "community" already means three things.** It is a node kind (`NODE_KIND=community`), a scale
   (`NODE_SCALE`, the framework's Community|City|Region|…, and `scales: [community]` in pack manifests; see
   `docs/site/concepts.md`), and the middle tier of the upstream-tiers design. A fourth meaning will confuse people. Either keep "community pack" and accept the overlap, or name this tier
   something else: *contributed*, *shared*, or *local*.
2. **Where the index lives.** Its own repository (`fabcity/planetai-packs` or similar) is the recommendation. The
   data registry is a list of sources, not of code, and mixing them makes both harder to read.
3. **Who may be listed.** Recommended: anyone, by pull request, with each entry marked `listed` or `reviewed`, and
   a code pack marked `reviewed` only once a maintainer has read its adapter.

## What this record does not do

It changes no code. It does not move any pack, rename any tier, or create the index repository. The per-node
override of an issue, beyond what a pack adds (point 4), is not decided here.
