# Packs: core, wild, and the door between them

**Question.** A city's packs arrived on 30 September as a fork of the whole node (#152): three packs, the shared
issue files edited around them, and two dashboard rows written into the shell. Which packs belong in the release,
where do the others live, how does a node get them, and how does one move from the second group to the first?

## What Tomas has said

On 1 October 2026, in the session that reviewed #152:

- Packs that are not core sit outside the release.
- Those packs are listed separately, and a node adds the ones it wants. That was the idea from the beginning.
- A pack from outside can become a core pack and go into the release.
- A pack adds to the main issues when it has something to add.
- Packs need room on the dashboard, and a way to sit in it without bringing a design of their own.

On 2 October 2026, answering the three questions this record left open:

- **The tier outside the release is called wild.** Core packs and wild packs.
- **The index lives in its own repository, and wild packs can live there too.**
- **Anyone may be listed, by pull request.**

The rest of this record is the recommendation those answers complete. Tomas decided it on 2 October 2026.

Later on 2 October, point 4's region source was taken out (below): it contradicted the rule from 11 September that
an issue never falls back to a second measure of the same idea. Tomas chose to leave the region column as it is.

## Recommendation

**1. Two tiers.**

| | core | wild |
|---|---|---|
| lives in | `packs/` in this repository | its own repository, or a folder in the wild index repository |
| reaches a node | in the release | `planetai packs add`, which fetches it into `packs/<id>` |
| gates | `make lint && make test`, every commit | its own tests, and the index repository's CI |
| maintained by | this repository's maintainers | its author |
| code (`adapter.py`) | runs with `PACKS_ALLOW_CODE=1` | the same, and nothing more |

The node needs no change to load a wild pack: it loads any folder under `packs/` with a `pack.yaml`, and
`planetai update` leaves a folder it does not track alone. `docs/PACKS.md` says how to fetch one by hand.

**2. One repository for the wild packs: the index, and a home.** It holds a list of every wild pack, wherever it
lives: where it is, what it reads, who wrote it, which node versions it was tested on. It can also hold a wild pack
as a folder, for an author who would rather not keep a repository of their own. Both are allowed. `planetai packs`
prints core and wild packs under separate headings.

Hosting a pack there is not adopting it. So:

- each hosted folder names its author in `CODEOWNERS`, and a change to that folder needs the author's review;
- each hosted folder says its licence in its README (code and data can differ, as they do here);
- one CI workflow runs `tools/check_rules.py` from this node's `main` and the pack's own tests over every hosted
  folder, on a schedule as well as on a push, because a gate that reads another repository's `main` goes stale
  without a commit of its own;
- every entry, hosted or not, is marked `listed` or `reviewed`, and a code pack is `reviewed` only once a maintainer
  has read its adapter.

**3. Promotion is a pull request.** A wild pack becomes core when a pull request moves its folder into `packs/`, it
passes every gate, and a maintainer here agrees to keep it. The tests a reviewer should ask for:

- it is useful beyond the place it was written for, or it is the reference for a pilot city;
- its data is openly licensed, and its README says under which licence;
- it has offline tests, registered in `tests/all`;
- somebody here will answer for it when it breaks.

The author line keeps the original author, and the index entry says where it went.

**4. A pack adds to an issue; it never replaces one.** Issues already take in a pack's rules and metrics by its
`domain:` (`packs: domains:` in each `app/issues/*.yml`). Extend the same claim to readouts, which a pack could not
add until #160:

- **Readouts.** A pack declares `readouts:` for an issue in its own manifest, and the node merges them in while the
  pack is installed. PSI and wind on Air, WBGT on Heat and the beach band on Coast would then travel with the
  Singapore packs instead of living in the shared files.
- **Not the region source.** This record first proposed an ordered list for an issue's `region:`, the first source
  with a fresh reading winning ("NEA, then CAMS"). That is a fallback, and `app/issues/__init__.py` refuses one on
  any distance, for the reason `app/issues/land.yml` gives (11 September 2026, #24): two numbers for one idea with
  different provenance is worse than one, because the column would switch between a measurement and a model with no
  way for a reader to tell. Tomas decided on 2 October 2026 to leave `region:` as it is. A pack that has a better
  regional number shows it as a readout (NEA's PM2.5 on Air, beside the CAMS region), and the region column stays
  one source. If a node one day needs a pack's number in the comparison itself, the option on the table is a pack
  *replacing* an issue's region source outright, with no fallback and an empty column when it goes quiet; nothing
  is built for that.

**5. Wild packs declare their dashboard sections; only core ships script.** A section in the page reads the same
browser storage the page keeps the admin token in, so a pack's own JavaScript would hold admin rights on every node
that installs it. Instead, a wild pack describes its section as data: the stage, the title, which of the four card
kinds (readout, stack, series, row) and which metrics fill it. The shell draws it with its own components, so it
looks like the rest of the page, the visual gate measures it, and the node still computes what the page draws. A
section that needs script is a reason to promote the pack.

**6. `requires:` is enforced.** Every manifest says which node versions it needs (`requires: { node: ">=0.40.0" }`)
and nothing reads it. The loader should refuse a pack its node is too old for, with one line in the log and in
`planetai packs`. This matters once packs are no longer released with the node they were written for.

## Fetching without git

A node installed the default way has curl and tar and no git (`install` says so in its header; git is only for
`PLANETAI_FROM_GIT=1`). So `planetai packs add` cannot be a `git clone`. It downloads the GitHub archive of one
commit and extracts either the whole repository or one folder of it into `packs/<id>`. That covers both homes in
point 2 with one mechanism. It writes where the pack came from and which commit beside it, so running `packs add`
again updates it and `planetai packs` can say how old it is.

Both extractions were run on 2 October 2026 against this repository's own `packs/heat`, with bsdtar 3.5.3 (macOS)
and GNU tar 1.35 (Ubuntu 24.04 and Debian, the `python:3.12-slim` image), including the archive of a pinned commit.

## What happens to the packs here now

Every pack in `packs/` today is core by this record, including the three whose author line says otherwise
(`xiaomi-air`, `posidonia`, `example-cooking-hours`). Whether any of them moves out is a decision per pack, and
not this one. Singapore's three (`singapore-nea`, `singapore-beach`, `fire-smoke`) start as wild packs. Saad has
been asked to move them out of #152; the wild repository is a home for them if he would rather not keep his own.

## Cost, in the order it should land

1. This record, and the fetch instructions in `docs/PACKS.md`.
2. The wild repository: the list, a `CODEOWNERS`, and the scheduled CI. It can open with Singapore's three packs.
3. `planetai packs add <owner>/<repo>[/<folder>][@<commit>]`: curl and tar, refuse an id a core pack already has,
   write the source and commit beside the pack, then `planetai packs install`. Bash and Python 3.9's standard
   library only, like the rest of the CLI. One test. `planetai packs` then lists core and wild apart.
4. Pack readouts, in `app/issues/` (#160). `tests/test_issues_engine.py` replays node #1 and came out identical. The
   ordered region list is not built; see point 4.
5. Declared sections in the shell. This is the design work. Singapore's two wall rows are the first case, and they
   may show that four card kinds are not enough.
6. `requires:` at load time. Small.
7. The word. Three comments still call every pack a "community" pack (`app/packs.py`, `docker-compose.yml`,
   `.env.example`). They change with step 3.

## What gets harder

- **Promotion collides with a fetched copy.** A node that fetched a wild pack into `packs/<id>` and then updates to a
  release where `<id>` is core: on a git checkout, `git pull --ff-only` refuses to overwrite the untracked folder;
  from the tarball, the release's files are unpacked over the old copy. `planetai update` should notice a fetched
  pack where a core pack is arriving, say what to remove, and stop.
- **Gates move out of this repository.** A wild pack is tested where it lives and by the index, not here.
- **The wild repository can turn into a second core.** If every hosted pack is quietly maintained by whoever
  maintains this repository, the tier means nothing. `CODEOWNERS` and the `listed` mark are there to keep that
  visible.
- **Trust.** A wild code pack runs with this node's privileges, as a core one does. Being listed is not being read.

## What this record does not do

It changes no code. It does not move any pack or create the wild repository. The per-node override of an issue,
beyond what a pack adds (point 4), is not decided here.

Decided: Tomas, on 2 October 2026.
