# The CLI's successor — decided before v1, started after Stage 1

**Raised 18 September 2026 by the design review. Drafted 20 September. Proposed, not decided.** Nothing
here is built, nothing is refactored, and the start date in §5 is deliberately not now.

---

## §1 · What `bin/planetai` is today

| | |
|---|---|
| lines of Bash 3.2 | **1,839** (the review said 1,731) |
| embedded Python snippets, each pinned to **3.9** by `tools/check_cli_python.py` | **29** |
| calls to `envget` | **51** |
| `.env` reader implementations in the repo | **2** — `bin/planetai:137` and `backup.sh:16`, near-identical, differing by one `\| head -1` |
| `docker` call sites across the five shell files | **99** (57 of them here) |
| one-shot wizards | **4** — `meshtastic` 58 lines, `agent_local` 37, `reticulum` 27, `homeassistant` 27 = **149** |
| `planetai doctor` | 62 lines, **18 checks** |

**Two constraints, both of them for macOS**, which `docs/PLATFORMS.md` ranks second:

- **Bash 3.2**, because that is what Apple ships and has shipped since 2007.
- **Apple's Python 3.9, stdlib only.** `tools/check_cli_python.py` compiles every embedded snippet with
  `feature_version=(3,9)` and refuses `import yaml`, `httpx`, `psycopg` and four more **by name** —
  because `planetai packs` once imported PyYAML and worked on the developer's machine and on no node.

**The doctor is not duplicated, and that matters to what follows.** `planetai doctor` has 18 checks; the
MCP `health_check` in `app/agent.py` has 5. They overlap on roughly three — the database answering, a
backup in the last two days, the poll being recent. The other fifteen — docker running, containers up,
disk free, the backup destination actually mounted, a nightly job scheduled, the release signature on
the last update — **need a host shell and cannot move into a container at all.** So `planetai` is not
going away under any option below. The question is only what it is written in.

## §2 · (A) Stay Bash, consolidate

The second-pass review's own recommendation. Split the four wizards into `tools/setup-*.sh`, collapse
the two `.env` readers into one sourced file, and keep the doctor as it is.

**Estimate: one week.**

- **Bash 3.2 and Python 3.9** stay exactly as they are. `tools/check_cli_python.py` stays.
- **`install-smoke.yml`** unchanged — the four legs already run the real installer end to end.
- **The 42 test suites** (43 once PR #95 lands; the review said 34) are unchanged. `tests/test_config.py`
  greps `bin/planetai`'s source, so a consolidation has to move its assertions with the code — an
  afternoon inside the week, and a warning about what that suite really tests. See (B).
- **A tester on a 2015 laptop** notices nothing, which is the point.

**What it does not fix:** every shell bug in the two September reviews is a bug Bash invites — an
unquoted expansion, a `set -e` interaction, a subshell that swallows an exit code. Consolidation makes
1,839 lines into perhaps 1,500 in five files and leaves the language the same.

## §3 · (B) One Python 3.9-stdlib file

The floor `tools/check_cli_python.py` already enforces, applied to the whole CLI instead of to 29
snippets. `argparse`, `urllib.request`, `json`, `subprocess`. `--json` on every command for free. The
Bash stub stays for `curl | bash` only.

**Estimate: three to four weeks — two to three for the CLI, and the rest for the behavioural test
harness that does not exist yet (see below). The review's "two to three weeks including parity tests"
assumed a harness to run parity against.**

- **Bash 3.2 stops being a constraint** for everything except `install` — which is the one file a
  stranger pipes into `bash`, and which must stay Bash forever.
- **Python 3.9 becomes a harder constraint, not a softer one.** Today it binds 29 snippets; then it
  binds 1,800 lines, on a version that reached end of life in October 2025. No `match`, no
  `tomllib`, no `|` unions, no `zoneinfo` without `tzdata` — and the app container is 3.12, so two
  Pythons with different capabilities live in one repository and a contributor has to know which file
  they are in. `tools/check_cli_python.py` would have to grow from "check the snippets" to "check the
  CLI", which is a much better gate and a much slower one.
- **`install-smoke.yml`** needs a leg proving `python3` exists and is ≥3.9 *before* the CLI runs. It
  already asserts `python3 present` in the preflight; the installer would now depend on it.
- **The test suites**: and here the honest answer is worse than the review's. There is **no
  behavioural CLI harness**. `tests/test_config.py` is the only CLI suite and it *"reads the files and
  asserts on them; no node needed"* — it greps `bin/planetai`'s source. A rewrite in another language
  makes it assert nothing, and there is nothing to run against the new command instead. **Building that
  harness is part of (B)'s estimate, not a thing (B) inherits**, and it is why two-to-three weeks is
  the optimistic end.
- **A tester on a 2015 laptop**: unaffected on macOS (Python 3.9 is there). On a stripped Debian,
  `python3` is not always installed — `install` would have to say so, and the preflight already checks
  it.

## §4 · (C) A static Go binary in the tarball

Cross-compiled in CI for `linux/amd64`, `linux/arm64`, `darwin/arm64`, `darwin/amd64`. No host
interpreter question at all.

**Estimate: three to four weeks, and a new language in the repository.**

- **Bash 3.2 and Python 3.9 both stop being constraints**, completely and permanently. That is the
  whole of (C)'s case and it is a real one: the two constraints that shape this repository's host-side
  code both exist because of what Apple ships, and a static binary makes Apple's choices irrelevant.
- **`install-smoke.yml`** gains a build matrix and the tarball gains four binaries — roughly 8–12 MB
  against today's whole tarball. The arm64 leg added in PR #94 already proves the CI shape.
- **The test suites**: the same missing harness as (B), and the same cost. And
  `tools/check_cli_python.py` is deleted, taking with it the only gate that has caught a class of bug
  ("works here, fails on every node") *before* a node saw it.
- **A tester on a 2015 laptop** gets a faster CLI and one more thing to trust: a binary they cannot
  read. Today `planetai` is a text file a keeper can open at 9pm and see what it is about to do to
  their database. That is not a small property for software that runs in somebody's house, and this
  project's own `AGENTS.md` and `CONTRIBUTING.md` lean on it.
- **And it is a third language** after Python and JavaScript, in a repository where 431 of 441 commits
  are by one person. That is the argument against (C) and it is not really about Go. (PR #96 drafts a
  `MAINTAINERS.md` and a `GOVERNANCE.md` that state it; neither is on `main` as this is written.)

## §5 · Recommendation

**(A) now, at the point it is needed; (B) after v1; (C) never, unless a platform forces it.**

1. **(A) is not a stepping stone, it is the correct immediate answer.** One week, no new constraint, and
   it deletes the duplicated `.env` reader — which is also step 5 of
   `docs/decisions/2026-09-18-config.md`, so the two records share a piece of work and it should be done
   once.
2. **(B) is the destination.** It removes the language that invites the bugs both September reviews
   found, and it keeps the CLI readable by the person whose house it runs in. Two costs, both real:
   Python 3.9 — EOL since October 2025 — as a hard floor for 1,800 lines, and a behavioural test harness
   that has to be written first. Re-examine both before starting; if macOS ships a newer Python by then,
   the first one gets materially cheaper.

   **And the harness is worth building whichever option wins**, because today nothing tests what
   `planetai` *does* — only what its source says.
3. **(C)'s case is the one that could win later.** If `install-smoke.yml` grows a platform where neither
   Bash 3.2 nor a usable Python is guaranteed — a BSD, a router, a very stripped container — the binary
   stops being a preference and becomes the answer. Nothing today is that platform.

### When it starts

**Not before the pilot has produced its evidence.** `PRODUCT.md`'s ninety-day test is *"five nodes
alive, at least one documented case where someone changed behaviour because of a message, and a price a
household will pay"*. Today there are **two** nodes and no documented case. (The review calls this
"Stage 1's trigger"; that phrase is not in `SPEC.md §6` or `PRODUCT.md`, so this record uses the
condition those files actually state.)

The reason is not caution. A CLI rewrite changes the thing every tester touches, during the only period
in which their reports are the evidence the product exists. `docs/NEXT_RELEASE.md`'s rule 3 — a release
ships one large change, not two — applies here with more force than anywhere else it is written.

So: **(A) whenever a week is free. (B) named in the release after Stage 1, and re-costed then, not now.**

---

## §6 · What this record does not do

It does not refactor anything, split a wizard, delete a key or move a line. `tools/check_cli_python.py`
is untouched and stays in `make lint`. The estimates are working numbers from the counts in §1, not
quotes — and the honest thing to say about a two-to-three-week estimate written by a machine that has
never maintained this CLI is that it is the least reliable number in this document.
